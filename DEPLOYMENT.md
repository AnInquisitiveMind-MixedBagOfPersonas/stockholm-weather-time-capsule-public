# Local verification, GitHub and AWS staging

Use this runbook from the Stockholm Weather Time Capsule repository.

## Prove Bedrock access locally

1. In [AWS Billing → Credits](https://console.aws.amazon.com/billing/home#/credits), check the expiry date and eligible services. Check that **Amazon Bedrock** is covered before running inference. Before staging, also check EC2, its gp3 disk and public IPv4 costs and coverage. Pause the relevant live step if coverage is unclear or unavailable. [AWS billing guidance](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier-plans-activities.html)
2. Open **Amazon Bedrock → Playground** in Stockholm (`eu-north-1`). Select Amazon Nova Lite and direct in-region inference if offered. Send one short prompt: “Write a short Stockholm dispatch using these facts only. The adjusted daily mean on 15 May 1897 was 9.6 °C. On 15 May 2026 it was 9.4 °C, 0.2 °C cooler. The General Art and Industrial Exhibition opened on Djurgården on 15 May 1897.” Check the values and comparison direction. [Nova Lite model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-lite.html)
3. Open the terminal configured for your AWS identity. If the AWS CLI is available, run `aws sts get-caller-identity` to confirm the intended account and identity. Use the same named profile for the CLI and the app if your setup requires one. The local identity needs `bedrock:InvokeModel` for each Stockholm model you test. Keep identity output and credentials out of shared logs. [AWS SDK credential sources](https://boto3.amazonaws.com/v1/documentation/api/latest/guide/credentials.html)
4. Create a virtual environment for the terminal you are using. In PowerShell, run `python -m venv .venv` and use `.venv/Scripts/python.exe`. In WSL or Linux, run `python3 -m venv ~/.venvs/stockholm-capsule` and use `~/.venvs/stockholm-capsule/bin/python`. Use that interpreter wherever this section says `python`. Install the hash-pinned wheels with `python -m pip install --require-hashes --only-binary=:all: --no-deps -r deploy/requirements.txt` and check them with `python -m pip check`.
5. Run one terminal Converse request using the same code and dataset as the app: `python -c "from datetime import date; from app import ROOT, WeatherArchive, dispatch_facts; from dispatch import BedrockDispatch; print(BedrockDispatch()(dispatch_facts(date(1897, 5, 15), WeatherArchive(ROOT / 'stockholm_daily_mean_temperature.csv'))))"`. This checks SDK authentication and permission separately from the browser. An access error calls for checking the profile, expiry and model permissions. Keep the provider set to Stockholm.
6. Run `python -B -m unittest discover -s tests -v` for the offline checks. Then start the local app with `python app.py --bedrock --port 8769` and visit [the local preview](http://127.0.0.1:8769/). Select **Create time capsule** on each date below. Compare the generated text with the source facts. A model response can still contain mistakes. Close the app with Ctrl+C when finished.
7. To verify Qwen through the app, stop the running preview and launch it from the project root in WSL with `CAPSULE_BEDROCK_MODEL=qwen ~/.venvs/stockholm-capsule/bin/python app.py --bedrock --port 8769`. Generate a dispatch for each date below. Launch with `CAPSULE_BEDROCK_MODEL=nova-lite` to explicitly select Nova Lite.

| Date | Expected evidence in this dataset snapshot |
| --- | --- |
| 15 May 1897 | 9.6 °C, compared with 9.4 °C on 15 May 2026. The newer date was 0.2 °C cooler. The exhibition opened on Djurgården. |
| 29 February 2000 | 3.8 °C, compared with 2.4 °C on 29 February 2024. The newer date was 1.4 °C cooler. The page has no curated historical event for this date. |

### Fix missing ensurepip in Ubuntu

Run `python3 --version` in the Ubuntu terminal. If it reports Python 3.12 and venv reports missing `ensurepip`, install the Ubuntu package with `sudo apt update && sudo apt install python3.12-venv`. Run `python3.12 -m venv ~/.venvs/stockholm-capsule` again, then verify with `~/.venvs/stockholm-capsule/bin/python -m pip --version`. Continue with the pinned dependencies once pip is available. If Ubuntu reports another Python version, identify that interpreter with `command -v python3` and check its matching venv support. [Ubuntu package](https://packages.ubuntu.com/noble/python3.12-venv), [Python virtual environments](https://docs.python.org/3.12/library/venv.html)

### Compare Nova Lite and Qwen from WSL

Use the existing Windows project folder through WSL's `/mnt/c` mount. From the repository root, run `aws --version` and `aws sts get-caller-identity --no-cli-pager`. If you use a named profile, select the same profile for all commands. Continue after confirming the intended AWS account and credit coverage.

Use the [comparison request](docs/bedrock-smoke-request.json) for both calls. It contains only the public weather and history facts, plus a fixed output limit. Run each command once.

- Nova Lite: `AWS_MAX_ATTEMPTS=1 aws bedrock-runtime converse --region eu-north-1 --model-id amazon.nova-lite-v1:0 --cli-input-json file://docs/bedrock-smoke-request.json --query '{stopReason: stopReason, text: output.message.content[].text}' --output json --no-cli-pager`
- Qwen: `AWS_MAX_ATTEMPTS=1 aws bedrock-runtime converse --region eu-north-1 --model-id qwen.qwen3-235b-a22b-2507-v1:0 --cli-input-json file://docs/bedrock-smoke-request.json --query '{stopReason: stopReason, text: output.message.content[].text}' --output json --no-cli-pager`

Record the model, its stop reason and dispatch, or the AWS error code. Check the result against the 1897 facts in the table above. A `max_tokens` stop reason indicates that the output limit was reached. Keep account identifiers and credentials out of the evidence you share. [AWS CLI Converse reference](https://docs.aws.amazon.com/cli/latest/reference/bedrock-runtime/converse.html)

## Install on a dedicated staging host

1. Check AWS credit coverage and sign in from your deployment terminal. Confirm the intended account, Stockholm region, existing public subnet, EC2 key pair and operator IPv4 address. The proposed staging costs include a `t3.micro`, an encrypted 8 GiB gp3 disk, a public IPv4 address and Bedrock inference. Use the [AWS Pricing Calculator](https://calculator.aws/#/) to estimate the demo duration and the expected calls. A budget alert helps track spending and the app limits generation per process.
2. In `deploy/terraform`, enter the approved `subnet_id`, `key_name` and `ssh_cidr` in local `terraform.tfvars`. Use a single IPv4 address in `/32` notation and leave `region` at `eu-north-1`. Run `terraform init` and review the generated provider lock. For use in both Windows and WSL, run `terraform providers lock -platform=windows_amd64 -platform=linux_amd64` in a terminal with registry access and save the reviewed lock in Git. Run `terraform validate` and `terraform plan -out=staging.tfplan`. The plan uses AWS data sources and your configured AWS identity.
3. Review the saved plan before applying it. For a fresh dedicated installation, expect an instance, a security group, SSH ingress, HTTPS egress, an EC2 role, a Bedrock permission policy and an instance profile. Check for unrelated resource changes. Confirm that SSH is limited to the one approved address and that `bedrock:InvokeModel` lists exactly Nova Lite and Qwen3 235B A22B 2507 in Stockholm. Generate a fresh plan if you have an earlier Nova Lite-only plan. Apply the reviewed plan with `terraform apply staging.tfplan`. Obtain the host using `terraform output -raw ssh_host`.
4. Verify the host's SSH key against the trusted EC2 console output. From the repository root, run `ansible-playbook -i '<host>,' -u ec2-user --private-key <local-key-path> -e capsule_dedicated_host=true -e capsule_bedrock=true -e capsule_bedrock_model=nova-lite deploy/install.yml`. The playbook configures the selected model, uses the instance role for Bedrock, installs the locked Python dependencies and checks the health endpoint. Run it again with the same options and investigate unexpected changes.
5. Open the tunnel with `ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8768:127.0.0.1:8080 -i <local-key-path> ec2-user@<host>`. Visit [the staging preview](http://127.0.0.1:8768/), check the date picker and generate a live dispatch. Rerun the playbook with `-e capsule_bedrock_model=qwen` and generate another dispatch to verify Qwen. Set the model you want for the demo and record the release commit, sanitised plan summary and results.
6. Check billing after the smoke test and again when usage has posted. When the demo is finished, create a fresh destroy plan with `terraform plan -destroy -out=cleanup.tfplan`. Verify that it targets only the dedicated staging resources. Apply that reviewed plan with `terraform apply cleanup.tfplan` and check that the instance and its associated resources have been removed.

## Open the protected demo link

Use the existing Stockholm EC2 host and the verified SSH key. Confirm that your Tailscale plan covers the demo. Keep the generated URL and the individual login details for invited colleagues.

1. **Create the logins on EC2.** Connect over your existing VPN-restricted SSH route. Run `sudo dnf install -y httpd-tools`. Create the first login with `sudo sh -c 'umask 077; test ! -e /etc/nginx/weather-capsule-demo.htpasswd && htpasswd -cB /etc/nginx/weather-capsule-demo.htpasswd demo-user-1'`. Enter the password when prompted. Add each additional colleague with `sudo htpasswd -B /etc/nginx/weather-capsule-demo.htpasswd demo-user-2`, using a different username and password for each. Use the same add command without `-c` to update an existing login. [NGINX authentication guide](https://docs.nginx.com/nginx/admin-guide/security-controls/configuring-http-basic-authentication/)
2. **Deploy the protected listener.** Back in Ubuntu, run this from the repository root with your verified host and key variables: `ansible-playbook -i "$CAPSULE_HOST," -u ec2-user --private-key "$CAPSULE_KEY" -e capsule_dedicated_host=true -e capsule_bedrock=true -e capsule_bedrock_model=qwen -e capsule_demo_access=true deploy/install.yml`. The playbook installs Tailscale, starts its service, configures Nginx on EC2 loopback port 8081 and verifies that unsigned GET and POST requests receive HTTP 401. In the EC2 shell, run `curl -fsS -u demo-user-1 http://127.0.0.1:8081/healthz`, enter the password at the prompt and check for `ok`.
3. **Limit Funnel permission to the staging instance.** In the Tailscale admin console, create the `tag:capsule-demo` tag with the tailnet administrator as its owner. In **Access controls**, scope the `funnel` node attribute to `tag:capsule-demo` and remove the broad `autogroup:member` Funnel entry if the console added it. Use a dedicated demo tailnet with no peer access grants to the tagged host. In the EC2 shell run `sudo tailscale up --hostname=weather-capsule-demo --advertise-tags=tag:capsule-demo --accept-dns=false --accept-routes=false`. Follow the sign-in link privately and confirm that the EC2 device has the demo tag. [Tailscale Linux installation](https://tailscale.com/docs/install/linux) · [Tailnet policy reference](https://tailscale.com/docs/reference/syntax/policy-file)
4. **Enable and verify the link.** In the EC2 shell run `sudo tailscale funnel --bg --https=443 http://127.0.0.1:8081`. Copy the generated HTTPS address from `sudo tailscale funnel status`. In a regular browser outside the SSH tunnel, check that unsigned and invalid logins are rejected. Sign in with a valid demo account and generate a Qwen dispatch for 29 February 2000. Check the readings in the table above, then reopen the date to verify the cache. Allow an hour after the live check for the full five-attempt allowance to become available. [Funnel commands](https://tailscale.com/docs/reference/tailscale-cli/funnel)
5. **Share and close access.** Share the link with invited colleagues and deliver their credentials privately. After the demo, run `sudo tailscale funnel reset` on the dedicated EC2 instance. Verify from a regular browser that the link is unavailable. Rerun the playbook with `-e capsule_demo_access=false` and remove the dedicated password file on EC2 with `sudo rm -- /etc/nginx/weather-capsule-demo.htpasswd`.

### Pause and resume between demo days

- To pause the link, run `sudo tailscale funnel reset` on EC2 and check the HTTPS address in a private browser window. To pause EC2 compute usage as well, choose **Stop instance** in the AWS console. Use the full shutdown procedure above when the demo has finished and the logins can be removed. [AWS stop and start guide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html)
- To resume after stopping EC2, choose **Start instance** and copy the current EC2 public IPv4 address into `CAPSULE_HOST`. Set `CAPSULE_KEY` to the existing Ubuntu private-key path in the current terminal. Check that the Terraform-managed SSH rule allows the public IPv4 of the current VPN connection with `/32`.
- If SSH prompts for a fingerprint after the EC2 address changes, verify the instance ID in AWS and compare the fingerprint and key type with the previously trusted host key. The EC2 system log may no longer include the fingerprint printed on first boot. [AWS console output guide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/troubleshoot-unreachable-instance.html#instance-console-output) · [cloud-init fingerprint logging](https://cloudinit.readthedocs.io/en/latest/reference/modules.html#keys-to-console)
- Once connected to EC2, run `sudo tailscale funnel --bg --https=443 http://127.0.0.1:8081` and check `sudo tailscale funnel status`. Open the HTTPS link in a private browser window and confirm that the login prompt appears and valid credentials open the app.

### Set the shared demo allowance

For a demo that needs ten Bedrock attempts per rolling hour, rerun the demo playbook command with `-e capsule_dispatch_limit=10` alongside the other demo options. The five-attempt setting is the default and can also be selected with `-e capsule_dispatch_limit=5`. Changing the setting restarts the app, which clears its in-memory dispatches and request counter. Check the new setting on EC2 with `systemctl cat weather-capsule.service | grep '^Environment=CAPSULE_DISPATCH_LIMIT='`.

## Trust boundaries

The browser reaches Nginx through the authenticated SSH tunnel. Nginx passes the original host to the loopback-only Python service, where it is checked before generation. The generation form uses a token and only sends a date. The app resolves that date to the public Bolin Centre record and curated archive facts on the server. Model text is escaped before rendering. No provider credentials are sent to the browser.

For demo access, Funnel terminates public HTTPS and forwards requests to EC2 loopback port 8081. The protected listener authenticates every request, strips the browser's Authorization header and passes the expected local Host header to Python. The password hashes stay in a restricted file on EC2.

The EC2 role uses temporary credentials and has permission for the two approved models in Stockholm. The selected model handles each new dispatch in one attempt. The app allows one generation at a time. Its rolling-hour limit is shared by all logins using the process and counts failed attempts. Reopening a date with a cached dispatch uses the saved text. Terraform state, plan files, credentials and unredacted screenshots stay local. [AWS Converse API permissions](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)
